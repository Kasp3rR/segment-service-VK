# Замеры получения сегментов пользователя

Дата: 15 октября 2026. Измеряется точный SQL, который вызывает
`Store.UserSegments` (`postgres.UserSegmentsQuery`). Копия: [query.sql](query.sql).

## Что сравнивалось

Составной B-tree индекс `(user_id, segment_id)` уже присутствовал в миграции 001
как первичный ключ. Он одновременно обеспечивает уникальность назначений.
Новая дублирующая миграция не нужна.

В отдельной временной схеме созданы таблицы из реальных миграций сервиса и данные.
Для первого варианта удалён только `user_segments_pkey`, для второго восстановлен
`PRIMARY KEY(user_id, segment_id)`. Индексы users/segments и индекс segment_id
остались одинаковыми. Текст SQL не менялся между вариантами.

**Это сравнение с экспериментально отключённым индексом, а не история ускорения
от коммита рефакторинга к текущему.** Запрос и индекс были реализованы раньше;
на этом этапе получено измеримое подтверждение их эффекта.

Запрос выбирает необходимые поля, ограничивает выборку user_id, связывает таблицы
по ключам и сортирует небольшую результирующую выборку. LEFT JOIN сохраняет различие
между существующим пользователем без сегментов (`[]`) и отсутствующим пользователем
(`404`) в одном согласованном SQL-запросе. Переписывать этот запрос без измеримого
преимущества не потребовалось. Код сервиса и бенчмарк используют одну константу SQL.

## Условия

- PostgreSQL 16.15, Docker, aarch64; клиент Go 1.25.14, macOS arm64.
- 200 000 пользователей, 100 сегментов, 2 000 000 назначений: по 10 сегментов каждому.
- Пользователь 100001; возвращаются 10 строк.
- Данные детерминированы: segment_id = ((user_id + k * 13) % 100) + 1, k = 0..9.
- Один клиент, одно соединение; simple protocol, без кеширования prepared statements.
- Перед измерениями VACUUM ANALYZE; после восстановления индекса ANALYZE.
- По 2 прогрева и 20 измерений для каждого варианта. Сначала без индекса, затем с индексом.
- PostgreSQL shared_buffers=128MB, work_mem=4MB, effective_cache_size=4GB,
  max_parallel_workers_per_gather=2, random_page_cost=4, seq_page_cost=1, jit=on.
- Кеши ОС/БД не очищались; сохранённые планы показывают shared hit. Холодный старт не измерялся.
- Локальная машина не была выделенным нагрузочным стендом. Остальные сервисы работали
  без специально созданной нагрузки. Это не прогноз производительности production.

## Результаты

| Вариант | Медиана Execution Time | Минимум | Максимум | Медиана времени вызова EXPLAIN из Go |
|---|---:|---:|---:|---:|
| Без составного индекса | 83,4215 мс | 80,483 мс | 133,591 мс | 87,3785 мс |
| С составным индексом | 0,281 мс | 0,179 мс | 0,368 мс | 3,0065 мс |

Отношение медиан серверного Execution Time — **296,87 раза**.
Это время выполнения SQL под EXPLAIN ANALYZE. Оно не включает планирование,
HTTP, код приложения и передачу ответа пользователю. Клиентские значения включают
планирование, сетевой обмен и получение EXPLAIN; это также не время HTTP-запроса.

Без индекса PostgreSQL выбирает `Parallel Seq Scan` по user_segments: фильтрация
2 млн назначений. С индексом — `Index Only Scan using user_segments_pkey`,
`Index Cond: user_id = 100001`, `Heap Fetches: 0`. В текстовых планах суммарные
shared buffers: 12912 против 11. Сортировка десяти результатов занимает 26 kB.

JSON-планы сохранены для первого измерения после прогрева. Текстовые планы сняты
отдельным дополнительным выполнением после серии; их время может отличаться от медианы.

```sh
TEST_DATABASE_URL='postgres://segments:segments_local@localhost:55432/segments?sslmode=disable' \
  make benchmark
```

Параметры: BENCH_USERS (200000), BENCH_REPEATS (20), BENCH_OUTPUT (docs/sql-benchmark).
Для собственного прогона без перезаписи сохранённых измерений:

```sh
BENCH_OUTPUT=/tmp/segment-benchmark make benchmark
```

Команда создаёт уникальную схему `segment_benchmark_<timestamp>` и удаляет её по
завершении. Таблицы приложения не меняются. Нужны права CREATE SCHEMA и место для
таблиц и индексов. После SIGKILL схема может остаться: её имя видно в PostgreSQL;
удалять следует только схему конкретного прогона. Обычные ошибки возвращают ненулевой код.
