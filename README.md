# Segment Service

Сервис управления пользовательскими сегментами для A/B-тестов.
Репозиторий: `Kasp3rR/segment-service-VK`. Разработка ведётся в ветке `dev`.

Реализованы HTTP API на **Gin**, PostgreSQL через **pgx/pgxpool**, SQL-миграции,
JSON-логи **zap**, распределение пользователей и обработка через **Apache Kafka**.
API сохраняет задания и transactional outbox; отдельный worker публикует батчи
и запускает четыре консьюмера одной группы.

## Запуск

Нужны Docker Engine и Docker Compose. Для локальной Go-разработки — Go 1.25+.

```sh
cp .env.example .env
docker compose up -d --build --wait
curl http://localhost:18080/readyz
```

API: `http://localhost:18080`. PostgreSQL: `localhost:55432`. Kafka: `localhost:29092`.
Compose создаёт топик с четырьмя партициями и запускает API и worker.
Worker проверяет наличие минимум четырёх партиций при старте.
Порты привязаны к loopback; `API_PORT` и `POSTGRES_PORT` можно изменить в `.env`.
Данные PostgreSQL сохраняются в Docker volume. `docker compose down` сохраняет этот volume.
При старте API автоматически применяет недостающие миграции.

```sh
docker compose logs -f api worker
docker compose down
```

Локальный запуск Go с базой в Docker:

```sh
docker compose up -d --wait postgres kafka kafka-init
set -a
. ./.env
set +a
make build
go run ./cmd/api
# В другом терминале с тем же окружением:
go run ./cmd/worker
```

Go-программы читают переменные окружения, `.env` автоматически загружает только Compose.

## Правила данных

- `user_id` задаёт клиент: целое число от 1 до 9223372036854775807. Повторное создание — `409`.
- `segment.id` генерирует PostgreSQL. `code` уникален, соответствует `[A-Z][A-Z0-9_]{0,63}`
  и неизменяем как через HTTP API, так и прямым SQL UPDATE.
- `name` содержит 1–200 Unicode-символов после удаления пробелов по краям;
  `description` — до 4000 символов, может быть пустым.
- PATCH меняет только переданные `name` и `description`. Пустой объект, `null`, изменение
  `code` и неизвестные поля отклоняются. Пустая строка очищает описание.
- Повторные PUT и DELETE участия возвращают `204`. Оба ресурса должны существовать;
  иначе возвращается `404`.
- Удаление сегмента каскадно удаляет его назначения. Повторное удаление сегмента — `404`.
- Список сегментов существующего пользователя без назначений — `[]`; отсутствующий пользователь — `404`.
- `(user_id, segment_id)` — уникальный первичный ключ и составной B-tree индекс.
  Отдельный индекс `segment_id` ускоряет каскадное удаление.

## REST API

POST и PATCH требуют `Content-Type: application/json`; максимальный размер тела — 64 KiB.
JSON должен содержать ровно один объект. Неизвестные поля отклоняются.

| Метод | URL | Успех |
|---|---|---|
| POST | `/segments` | 201, созданный сегмент и Location |
| GET | `/segments?limit=100&after_id=0` | 200, массив сегментов |
| GET | `/segments/{id}` | 200, сегмент |
| PATCH | `/segments/{id}` | 200, обновлённый сегмент |
| DELETE | `/segments/{id}` | 204 |
| POST | `/users` | 201, пользователь |
| PUT | `/users/{user_id}/segments/{segment_id}` | 204 |
| DELETE | `/users/{user_id}/segments/{segment_id}` | 204 |
| GET | `/users/{user_id}/segments` | 200, массив сегментов |
| POST | `/segments/{id}/distributions` | 202, задание и Location |
| GET | `/distributions/{job_id}` | 200, состояние задания |
| GET | `/healthz` | 200, процесс работает |
| GET | `/readyz` | 200, PostgreSQL доступна; иначе 503 |

Список сегментов сортируется по `id`, `limit` от 1 до 1000 (по умолчанию 100).
Для следующей страницы передайте последний полученный `id` как `after_id`.
Сегменты пользователя тоже сортируются по `id`.

Ошибки имеют вид:

```json
{"error":{"code":"not_found","message":"resource not found"}}
```

Коды: 400 — неверные данные; 404 — ресурс отсутствует; 409 — конфликт уникальности, активное задание или превышение целевого числа;
413 — слишком большое тело; 415 — неверный Content-Type; 504 — истёк срок выполнения.
Внутренние ошибки базы клиенту не раскрываются.

## Примеры curl

```sh
BASE=http://localhost:18080
curl -i -X POST "$BASE/users" -H 'Content-Type: application/json' \
  -d '{"user_id":42}'

curl -i -X POST "$BASE/segments" -H 'Content-Type: application/json' \
  -d '{"code":"MAIL_GPT","name":"GPT в письмах","description":"Эксперимент почты"}'
```

Подставьте `id` созданного сегмента:

```sh
SEGMENT_ID=1
curl "$BASE/segments?limit=100"
curl "$BASE/segments/$SEGMENT_ID"
curl -i -X PATCH "$BASE/segments/$SEGMENT_ID" -H 'Content-Type: application/json' \
  -d '{"name":"GPT-помощник","description":""}'
curl -i -X PUT "$BASE/users/42/segments/$SEGMENT_ID"
curl "$BASE/users/42/segments"
curl -i -X DELETE "$BASE/users/42/segments/$SEGMENT_ID"
curl -i -X DELETE "$BASE/segments/$SEGMENT_ID"
```

## Распределение через Kafka

```sh
curl -i -X POST "$BASE/segments/$SEGMENT_ID/distributions" \
  -H 'Content-Type: application/json' -d '{"percent":30}'
JOB_ID=идентификатор_из_ответа
curl "$BASE/distributions/$JOB_ID"
```

`percent` — JSON-число от 0 до 100 включительно, допускаются дроби. Расчёт точный,
без float64: `floor(snapshot_users * percent / 100)`. Числовая запись ограничена
64 символами и модулем экспоненты 1000. При 7 пользователях и 30% результат — 2.

Один SELECT получает список пользователей вместе с текущим участием в сегменте.
Его MVCC-снимок определяет и `snapshot_users`, и множество кандидатов. Созданные после
этого SELECT пользователи в задание не попадают. На время планирования строка сегмента
блокируется; затем активное задание запрещает ручное изменение назначений, удаление
сегмента и повторный запуск распределения (`409`). Остальные сегменты и создание
пользователей доступны. Метаданные сегмента можно редактировать.

Существующие участники сохраняются. Если их больше цели — `409`, без создания задания.
Недостающие выбираются по возрастанию SHA-256 от двух int64 (`segment_id`, `user_id`),
закодированных big-endian, затем по user_id при равном хеше. Это даёт воспроизводимый
псевдослучайный выбор при одинаковых входных данных. Если добавлять некого, задание сразу
`completed`, без сообщений Kafka.

| Поле задания | Значение |
|---|---|
| `snapshot_users`, `target_users` | размер снимка и итоговая цель |
| `existing_users`, `planned_users` | уже назначенные и требуемое добавление |
| `assigned_users` | новые назначения, успешно записанные этим заданием |
| `batch_count`, `processed_batches` | общее и завершённое число батчей |
| `status` | queued, running, retrying, completed, failed |
| `last_error`, `retry_count` | последняя ошибка и число зарегистрированных повторов |
| `completed_at` | время завершения или окончательной ошибки |

Задание и все батчи до 5000 пользователей фиксируются одной транзакцией в PostgreSQL.
Публикатор забирает outbox через `FOR UPDATE SKIP LOCKED`, отправляет в Kafka с
`acks=all` и только после подтверждения помечает публикацию. Батч N направляется
в партицию N modulo количество партиций. Сбой между отправкой и отметкой может
привести к повторному сообщению; это ожидаемая доставка at least once.

Четыре консьюмера имеют разные соединения с PostgreSQL и параллельно обрабатывают
партиции. Запись назначений и `processed_batches(job_id,batch_number)` атомарна;
уникальность `(user_id,segment_id)` дополнительно защищает от дублей. Счётчики задания
обновляются под блокировкой строки. Последний батч проверяет итоговое число назначений.
Kafka offset подтверждается после коммита. При ошибке консьюмер повторяет то же сообщение,
не переходя к следующему; после перезапуска неподтверждённое сообщение безопасно повторяется.

Временные ошибки повторяются с задержкой: публикация 1–32 секунды, обработка 0,1–5 секунд.
`retrying` показывает сохранённую ошибку, `running` — успешную обработку очередного батча.
При недоступной БД записать состояние ошибки невозможно; она остаётся в логах,
сообщение не подтверждается. API может принять задание при недоступной Kafka:
оно сохраняется в outbox и будет отправлено после восстановления worker/брокера.

Несоответствие сообщения сохранённому outbox или повреждённый JSON сохраняются в
`kafka_dead_letters` перед подтверждением offset. Нарушение ограничений назначения
переводит задание в `failed`. Уже завершённые батчи сохраняются; после устранения причины
можно запустить новое задание, учитывающее эти назначения. История задания сохраняется
после удаления сегмента. Прямые изменения таблиц в обход API не входят в гарантии
согласованности; интеграционные тесты используют их для имитации повреждений и сбоев.

| `KAFKA_GROUP` | `segment-service` | группа четырёх консьюмеров |

| `OUTBOX_POLL_INTERVAL` | `250ms` | интервал опроса outbox |
| `WORKER_TIMEOUT` | `15s` | таймаут одной попытки worker, минимум 6s |

Значения `.env.example` предназначены для локального запуска. При SIGTERM/SIGINT
API прекращает приём новых соединений, завершает текущие запросы и закрывает пул БД.

## Миграции

SQL хранится в `internal/postgres/migrations` и встраивается в Go-бинарники через `embed`.
Применение защищено advisory lock PostgreSQL, выполняется в транзакции; версия и SHA-256
каждой миграции фиксируются в `schema_migrations`. Изменение уже применённого файла — ошибка запуска.

```sh
# Применить все новые миграции; DATABASE_URL должен быть в окружении.
go run ./cmd/migrate -direction=up
# Откатить последнюю миграцию. Откат 001 удаляет таблицы и их данные.
go run ./cmd/migrate -direction=down
```

Из контейнера:

```sh
docker compose run --rm --entrypoint /app/migrate api -direction=up
```

## Проверки

```sh
make check
make build
make test
make coverage
TEST_DATABASE_URL='postgres://segments:segments_local@localhost:55432/segments?sslmode=disable' \
  make integration
TEST_DATABASE_URL='postgres://segments:segments_local@localhost:55432/segments?sslmode=disable' \
  TEST_KAFKA_BROKERS=localhost:29092 make integration-kafka
```

`make test` включает детектор гонок. Интеграционные тесты требуют реальную PostgreSQL:
каждый тест создаёт собственную схему и удаляет её после завершения; пользователь БД
должен иметь право создавать схемы. Таблицы приложения не очищаются.
`-tags=integration` без `TEST_DATABASE_URL` завершается ошибкой, а не пропуском проверок.

Модульные тесты охватывают бизнес-валидацию, ошибки, конфигурацию и JSON.
Интеграционные — CRUD, весь HTTP-сценарий, ограничения БД, миграции, параллельные назначения,
идемпотентность и конкурентное изменение разных полей сегмента.
Kafka-тесты создают отдельные топики и группы, проверяют четыре консьюмера, offset,
повторы, ошибки и восстановление. Нужны права создания/удаления топиков.
Фактические результаты: [этап 2](docs/stage-2-verification.md),
[этапы 3–4](docs/stage-3-4-verification.md).

## Автоматическая демонстрация на существующих данных

Для Go-команд экспортируйте окружение из `.env`:

```sh
set -a
. ./.env
set +a
make demo
```

`make demo` создаёт или находит `MAIL_GPT`, запускает 30%, опрашивает состояние,
проверяет число участников в PostgreSQL и наличие сегмента у выбранного пользователя
через HTTP. По умолчанию API_URL=http://localhost:18080; DATABASE_URL должен указывать
на ту же базу, что и API. Общий таймаут — 2 минуты, настраивается флагом:

```sh
go run ./cmd/demo -url http://localhost:18080 -timeout 3m
```

Демонстрация использует только пользователей, уже находящихся в БД, и не создаёт новых.
Если в базе 70000 пользователей и назначений ещё нет, ожидается 21000 назначений,
пять батчей и completed.
Повторная демонстрация сохраняет существующий сегмент: если цель уже достигнута,
новое задание сразу completed, planned_users=0. Если уже назначено больше 30% или
другое задание активно, команда возвращает ошибку 409. Она не удаляет назначения
ради демонстрации. Для проверки пользователя нужно минимум четыре пользователя в базе.

Без установленного Go эта программа доступна в Docker-образе:

```sh
docker compose up -d --build --wait
docker compose run --rm --no-deps --entrypoint /app/demo api -url http://api:8080
```

## SQL-замеры и итоговая проверка

```sh
make benchmark
make verify
```

`make benchmark` требует TEST_DATABASE_URL и создаёт изолированную временную схему.
`make verify` запускает форматирование/vet, сборку всех программ, модульные тесты,
покрытие бизнес-логики и интеграционные проверки с реальными PostgreSQL и Kafka.
Нужны TEST_DATABASE_URL и TEST_KAFKA_BROKERS; они заданы в `.env.example`.

На 2 млн назначений медиана Execution Time составила 83,4215 мс без составного индекса
и 0,281 мс с индексом. Индекс существовал до этого этапа; сравнение проведено с его
экспериментальным отключением в отдельной схеме. Это не замер HTTP latency.
[Условия, SQL, все измерения и EXPLAIN ANALYZE](docs/sql-benchmark/README.md).

## Как читать код

Стиль организации кода приведён к [article-project](https://github.com/Kasp3rR/article-project):
небольшие файлы по операциям, отдельные структуры запросов и последовательная обработка ошибок.

1. `internal/httpapi/router.go` регистрирует маршруты через `NewRouter`.
2. `internal/httpapi/dto.go` описывает входные данные; `segments.go`, `users.go`
   и `distributions.go` разбирают запрос и вызывают сервис.
3. `internal/service` проверяет данные. Каждая основная операция находится в отдельном файле.
4. `internal/postgres` выполняет SQL и управляет транзакциями. `distribution.go` создаёт задание,
   `outbox.go` отвечает за публикацию, `batches.go` сохраняет назначения.
5. `internal/queue/worker.go` запускает публикатор и четыре консьюмера;
   `producer.go` отправляет батчи, `consumer.go` обрабатывает сообщения и подтверждает offset.

[Результаты проверки рефакторинга](docs/refactoring-verification.md).

## Ограничения

Compose рассчитан на локальную демонстрацию: один Kafka-брокер, replication factor 1,
без TLS/SASL, авторизации API и автоматического архивирования outbox/истории/DLQ.
Запускается один worker с четырьмя консьюмерами; увеличение числа worker увеличит
число участников группы. Worker readiness проверяет зависимости и топик, а не завершение
ребалансировки группы. После старта группа может собираться несколько секунд.

Планирование выполняется синхронно до ответа 202: O(N) памяти и O(N log N) сортировки,
ограничено REQUEST_TIMEOUT. Асинхронная часть — массовые назначения через Kafka.
Для больших баз понадобится отдельная оптимизация планирования. Пока job активен,
ручные назначения этого сегмента заблокированы, включая время недоступности Kafka.
Автоматической отмены задания нет; временные ошибки повторяются до восстановления.

Результаты SQL-замеров сохранены в [отчёте](docs/sql-benchmark/README.md).
Итоговые проверки и демонстрация: [этапы 5–6](docs/stage-5-6-verification.md).
